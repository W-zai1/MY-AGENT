# 工程库更新报告（累积）

> **用途**：工程测试库每次小版本迭代都往这里**追加一条**。发布库发正式版时，
> **从这里取"待发布"的内容**决定这一版对外说什么；发完把对应条目移入"已发布"。
>
> **读者**：写工程库代码的人 / agent（追加），以及发正式版的执行者 / agent（消费）。
> **本文件位置**：`docs/internal/` ⇒ **不随发布库分发**（构建发布库时整目录排除）。
> 它是"内部账本"，发布库那份是给使用者看的 `CHANGELOG.md`，由发布流程**生成**。

---

## 一、发布闸门（什么时候才该发一次正式版）

**发布库不频繁更新**。工程库可以一天发好几个小版本，正式版只在**攒够内容**时才发一次。

满足**任意一条**才建议发：

| # | 条件 |
|---|---|
| 1 | "待发布"里累积了 **≥ 3 条「使用者可见」** 的变更 |
| 2 | 有 **1 条重要变更**：新增 / 改变使用者可感知的能力，或修复影响可用性的缺陷 |
| 3 | 距上次发布 **≥ 1 个月**，且"待发布"里至少有 1 条使用者可见变更 |
| 4 | 有必须尽快给到使用者的修复（安全 / 数据 / 可用性）—— 不受前三条限制，立即发 |

**不满足就不发**：继续在工程库迭代，不要在发布库刷版本号。
理由很实际 —— 使用者的更新器是手动点的，版本号刷太密会让人不再认真看更新内容；
而"发布"本身要走一遍构建 + 校验 + 端到端验证，是有成本的。

> ⚠️ 版本号只能**单调递增且同套格式**（更新器用字符串相等判断新旧）。
> 发布库用三段式（`1.001`、`1.002`…），工程库用递增整数（`104`、`105`…）。

---

## 二、条目格式（严格照此写，方便机器/agent 解析）

每个小版本一段，**追加在"待发布"区的最上方**（最新在上）：

```markdown
### <工程库版本> · <YYYY-MM-DD> · <类型>
- **标题**：一句话说清改了什么（要能让使用者看懂）
- **变更**：具体内容，可多行
- **影响文件**：`路径`、`路径`（发布库构建时需要关注的）
- **使用者可见**：是 / 否
- **进正式版**：需要 / 不需要（给理由）
- **验证**：跑了哪些测试、结果如何
```

类型取值：`功能` / `修复` / `内部` / `文档` / `性能`。

**"使用者可见"的判定**：装了这个新版本的使用者，能不能感觉到差别？
- 能（界面、行为、默认值、报错文案、性能）⇒ **是**
- 不能（测试、内部文档、发布流程、代码整理、只为工程库服务的脚本）⇒ **否**

只有"使用者可见 = 是"的条目才计入发布闸门的条数。

### v117 · 2026-10-13 · 修复
- **标题**：修掉外部工具**别名的无意义后缀**（审计 §15 的 P0-3），带 **1 遍别名迁移**
- **背景**：`registry.load()` 里有两句

      tool.alias = ALIAS_OVERRIDES.get(name) or self._alias_external(name, rel, used)
      if tool.alias in used:                    # ← 必然成立
          tool.alias = self._alias_external(name, rel, used)

  而 `_make_alias()` **自己会 `used.add()`** ⇒ 那句 `if` 必然为真 ⇒ **每个工具被生成两遍**、
  别名永远带一个无意义后缀。实测本机 **147 个**受影响：108 个 `_2`，
  另 39 个被顶到 `_4`/`_6`/…/`_80`（双重生成让**同基名**工具每次跳 2 ⇒
  40 个中文名工具全落在 `tool` / `tool_2` / … / `tool_80` 家族）。
- **⚠️ 这段代码长期被一句"刻意冻结"的 docstring 保护着**，理由成立：
  `tool_overrides.json` 与 `invocation_templates.json` **按 alias 索引**
  （`risk_grades.json` 按 tool name），改别名会让覆写**静默失效、闸门悄悄变松、不报任何错**。
  ⇒ 所以本条**不是删掉一句话**，而是三件一起做：
  1. **算法**：调用点去掉那第二遍生成（`_alias_external` 仍只做一次 `_make_alias`）；
     并补上"覆写值撞车时退回自动名"的分支，保住"别名唯一"。
  2. **迁移**：新增 `legacy_alias_map()` —— 把**同一份 `tools.json`** 在
     「旧双重生成」与「新单次生成」两套算法上各跑一遍，得出 `{旧别名: 新别名}`；
     `migrate_alias_keys()` 据此改写两份**按别名索引**的配置
     （`registry._load_overrides()` 与 `executor.load_templates()` 都调它 ——
     保证两份配置不会只迁一半），改写经 `config_io.write_json_atomic`（带备份 + 审计），
     **没改名就不落盘**。
     ⚠️ **映射是运行时算的、不是写死一张表**：别名由 `tools.json` 推导，而那份清单在别的
     机器上是**用户自己的工具箱** —— 写死只能覆盖本机，换台机器就迁移不到，
     而那恰好是"覆写静默失效"最危险的场景。
     ⚠️ **目标键已被占用时不覆盖**（覆盖会静默丢掉另一条配置，比不迁移更坏），
     保留原名并打印告警。
  3. **自检**：`test_v117_alias_migration.py`（**45 项**）。
- **本机实测结果**：`_2` 结尾 **108 → 1**（剩的 1 个是真实重名）；147 条映射；
  别名总数 216 **仍然唯一**；`webshell_2` → `webshell` 等全部就位；
  **三份配置的键 0 死条目**（`test_registry` 的"配置无死条目"断言也仍然绿）。
  ⚠️ 本机 `tool_overrides.json`（21 条）与 `invocation_templates.json`（44 条）
  **0 条带数字后缀** ⇒ **本次实际改写 0 条**，迁移逻辑是为**别的机器**准备的。
- **影响文件**：`app/registry.py`、`app/executor.py`、`run_all_tests.py`、
  `test_v117_alias_migration.py`（新）、`VERSION.txt`
- **使用者可见**：**是** —— 模型看到的工具名从 `webshell_2` 变回 `webshell`、
  `burp_2` 变回 `burp`（对**小模型的工具选型**有实际帮助：一长串 `_2`/`_80` 只能靠
  description 猜）。已配过覆写的用户**不受影响**（键自动迁移）。
- **进正式版**：**需要**（与 v115/v116 一起发 1.007）。
- **验证**：新增 `test_v117_alias_migration.py`（45 项）—— 其中**决定性**的一条是
  「实际别名序列 == 单次生成算法的结果，**逐项同序**」（比"有没有 `_2` 后缀"之类的启发式
  强得多：后缀可能来自**文件名**如 `Struts2-19检测工具` 的 `19`，也可能来自**真实重名**，
  启发式分不清这两者）；另有迁移幂等、不覆盖已占用键、保留 `_说明`、
  三份配置 0 死条目等断言。

- **⭐ 实现层面的额外发现（原报告没抓到，本轮实测发现）**：
  `_kill_tree` 自身**顺序是反的** —— 原先「先 `proc.kill()`，再 `taskkill /T /F /PID`」。
  而 `taskkill /T` 要靠**父进程还活着**才能枚举子孙；父进程一被杀，父子链就断，
  taskkill 只能报"找不到进程" ⇒ **孙进程照旧活着**。
  本机真起「父 → 孙」两层进程 + 心跳文件判定存活，三组对照：
  · 先 kill 再 `taskkill /T` → 孙进程**存活**  ← 旧实现
  · 先 `taskkill /T` 再 kill → 孙进程**死亡**
  · 只 `taskkill /T /F` → 孙进程**死亡**
  ⇒ 改为「先 taskkill 整棵树，失败才兜底 `proc.kill()`」。
  **这个错误自 v012 就在，四个调用点全受影响** —— 也就是说"取消"那条路径
  其实也一直没杀到孙进程。原报告 P0-2 只说"超时不杀树"，根因比它说的更深。

## 五、维护约定

- **每发一个工程库小版本，就追加一条**（哪怕"使用者可见：否"也要记 —— 否则下次发版时
  没人说得清"这期间到底改了什么"）。
- 追加时**顺手更新第一节的闸门判断**：若已满足条件，在提交说明里点一句
  「已达到发布闸门，建议安排一次正式版」。
- 发正式版时：从"待发布"取「使用者可见 = 是」的条目 → 写成发布库的用户可见
  `CHANGELOG.md` 与该版发布说明 → **把条目移入"已发布"** 并写明对应的发布版本号与提交。
- 本报告**不进发布库**。使用者看到的是由它生成的那份 `CHANGELOG.md`。

### ⚠️ 两个仓库都**不是单写入者**

发布库可能被**独立更新**（不经本手册；本报告记录里 `2bcefa1` 与 `1e79cf6` 就是这样来的），
工程库也可能被别的会话/agent 直接提交（`350f619` 就是这样来的）。所以：

1. 每次发布前**先 fetch 两个仓库**，确认：
   · 工程库本地 = 远端（否则你发布的基线是旧的）；
   · 发布库远端是否已经前进（可能你要发的内容已经发过了，或版本号已被占用）。
2. 发布库里发现的新提交，**不要当成异常去覆盖** —— 先读它的提交说明，判断是否需要
   把其中的修复**回移工程库**（否则两边逻辑会漂移）。
3. 报告与手册如果与实际不符，**以实际为准并回来改文档**，不要让文档变成"过期的权威"。
