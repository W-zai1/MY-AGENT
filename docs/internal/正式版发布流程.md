# 正式版发布流程（面向执行者 / agent 的操作手册）

> **读者**：被指派"发布正式版"的执行者（人或 agent）。按顺序做，每步都有断言，**不要跳步**。
> **本文件位置**：工程测试库 `docs/internal/`。它属**内部流程文档**，构建发布库时**整目录排除**
> （发布库只给使用者看，不发布我们自己的开发流程）。
> **适用范围**：把工程测试库的当前状态裁剪、发布为正式版，推送到**发布库**。
>
> **配套文件**：`docs/internal/更新报告.md`（工程库累积更新账本）。
> **要发什么、什么时候发，以它为准** —— 本手册只讲"怎么发"。

---

## 0. 先读懂两个仓库的分工

| | **工程测试库**（本仓库） | **发布库** |
|---|---|---|
| 角色 | 日常迭代、跑全套回归 | 只放运行组件，对外分发 |
| 内容 | 全部组件 + 全套 `test_*` + 内部文档 | 运行组件 + 面向使用者的 README + LICENSE |
| 谁在用 | 开发与联调 | 使用者的 `update.exe` 拉取更新 |
| 分支 | `main` | **必须 `main`**（更新器读 `refs/heads/main`，写死在 `update.py`） |
| 版本号形式 | 递增整数（`102`、`103` …） | 三段式（`1.001`、`1.002` …） |
| 更新节奏 | **每个小版本都推**（日常迭代） | **攒够才发**（见 §2 发布闸门，不频繁更新） |
| 变更记录 | `docs/internal/更新报告.md`（累积账本） | 由报告生成的 `CHANGELOG.md`（使用者可见） |
| 是否有 `release_repo.txt` | **不放**（且已 gitignore） | **必须有**（指定自身仓库名） |

**四条硬约束**（违反任何一条都会出静默故障，不是报错）：

1. `update.py` 在两库必须**逻辑一致**：代码行（去掉注释与空行）完全相同，
   **只允许 `DEFAULT_REPO` 的值不同** —— 工程库指向工程库、发布库指向发布库
   （发布库那份还要能在 `release_repo.txt` 丢失时独立工作）。
   ⚠️ 早期（v103）曾要求"逐字节一致"，但自发布库 1.002 起发布库把内置默认源改成了自己，
   逐字节不再成立。核对方法：两边各去掉注释/空行、把 `DEFAULT_REPO` 的值归一，再逐行比。
2. 发布库的 `VERSION.txt` 与 `SHA256SUMS.txt` 必须在**同一个 commit** 内更新。
3. `SHA256SUMS.txt` 必须**从 git index 的 blob 生成**，绝不从工作区文件生成（原因见 §11.1）。
4. 发布库**不得包含**：`release_repo.txt` 以外的本地覆盖文件、任何 `test_*`、任何内部文档
   （含 `docs/internal/` 整目录）。

> ⚠️ **两个仓库都不是单写入者**：发布库可能被独立更新（不经本手册），工程库也可能被
> 别的会话/agent 直接提交。**开始之前先 `git fetch` 两边**并读一遍发布库的新提交 ——
> 详见《更新报告》§五「两个仓库都不是单写入者」。

> 具体路径与仓库名属本机信息，**不在本文档里写死**。执行前确认：
> 工程库 = 本文件所在仓库根；发布库工作副本 = 本地一个独立的 git 仓库工作副本，
> 其 `release_repo.txt` 第一行即发布库的 `owner/repo`。

## 1. 前置条件（缺一条就别开始）

```bash
# 1) 先 fetch 两边（两库都不是单写入者，见 §0 的说明）
git -C <工程库> fetch origin
git -C <发布库工作副本> fetch origin

# 2) 工程库干净、本地 = 远端
git -C <工程库> status --porcelain        # 期望：无输出
git -C <工程库> rev-parse HEAD
git -C <工程库> ls-remote origin refs/heads/main   # 两者必须相同

# 3) 全量回归 0 失败（必须，不是"看着还行"）
python run_all_tests.py                   # 期望：合计 N 项通过 / 0 项失败

# 4) 发布库仓库已存在且可写（推送需要凭据）
git ls-remote https://github.com/<owner>/<repo>.git
```

⚠️ **发布库可能已经前进**：先看 `git -C <发布库> log --oneline -5`。
若远端有你不知道的提交，**先读它的提交说明**再决定（可能你要发的内容已经发过，
或版本号已被占用）。发现修复类提交时，考虑是否需要**回移工程库**，否则两边逻辑会漂移。

若工程库有未推送的提交：**先推工程库**，再开始发版。发布库的内容应当来自一个
"已推送、且回归全绿"的确切提交 —— 否则你发布的版本在仓库里找不到对应来源。

## 2. 判定"能不能发"

### 2.1 第一道闸：**内容攒够了吗**（发布库不频繁更新）

工程库可以一天发好几个小版本；**正式版只在攒够内容时才发**。先打开
`docs/internal/更新报告.md`，看"待发布"区里有多少条 **「使用者可见 = 是」** 的条目：

满足**任意一条**才继续往下走：

| # | 条件 |
|---|---|
| 1 | 待发布里累积了 **≥ 3 条**使用者可见的变更 |
| 2 | 有 **1 条重要变更**（新增/改变使用者可感知的能力，或修复影响可用性的缺陷） |
| 3 | 距上次发布 **≥ 1 个月** 且至少有 1 条使用者可见变更 |
| 4 | 有必须尽快给到使用者的修复（安全/数据/可用性）—— 不受前三条限制 |

**不满足就停在这里**，不要为了"有更新"而刷版本号：使用者的更新器是手动点的，
版本号刷太密会让人不再认真看更新内容，而每次发布都要走一遍构建 + 校验 + 端到端验证。

> 若"待发布"里一条使用者可见的都没有（例如只改了测试、内部文档、发布流程本身），
> 结论就是**这一轮不发正式版** —— 这是正常状态，不是流程出了问题。

### 2.2 第二道闸：技术条件

- 全量回归 **0 失败**（跳过项要能解释，例如"环境未就绪"类）；
- 本次要发布的功能已合入 `main`，且**已在工程库推送到远端**；
- 没有正在进行的改动把这批文件改到一半。

### 2.3 必须写进发布说明的三件事

1. **版本号格式**：更新器用**字符串相等**判断新旧，不做大小比较 ⇒ 此后必须始终用同一套格式递增。
   忽而 `1.1` 忽而 `1.001`，更新器会永远认为"有新版本"而反复触发更新。
2. **更新只新增/覆盖文件，不会删除** ⇒ 老用户从工程库更新到发布库时，本机残留的
   `test_*.py` 等文件**不会被清掉**，需要人工清理。"仓库整洁"只对新安装生效。
3. **更新源**：更新器从 `release_repo.txt` 指定的仓库拉取。要换库只改这一行，
   不必重新打包 `update.exe`。

### 2.4 这一版对外说什么：从《更新报告》生成 `CHANGELOG.md`

发布库该带一份**使用者可见**的 `CHANGELOG.md`，内容**从报告里"使用者可见 = 是"的条目改写**：

- 一条内部条目可能拆成/合并成几条用户可见的说法；
- **去掉内部细节**：内部文件路径、函数名、测试名、架构讨论、本机信息一律不写；
- 保留：能感知到的行为变化、新的默认值、界面/文案变化、修复的现象；
- 写法从使用者视角出发（"现在可以在起始页选黑盒/白盒"而不是"新增 MODES 注册表"）。

> 报告本身**不进发布库**（`docs/internal/` 构建时整目录排除），
> 只把生成出来的 `CHANGELOG.md` 随发布库走。

## 3. 构建发布库工作副本

### 3.1 ⚠️ 必须用 `git archive`，不要用文件系统复制

```bash
cd <工程库>
git archive --format=tar HEAD -o /tmp/release.tar
mkdir -p <发布库工作副本>
tar -xf /tmp/release.tar -C <发布库工作副本>
```

**为什么不能直接 `cp -r` 工作区**：

- `git archive` 导出的是**仓库内容（被跟踪文件）**，天然不含 gitignored 的本机数据 ——
  授权白名单、代码库登记、SQLite 库、`artifacts/`、`scripts/`、`config.yaml`、`update.exe`
  **一个都不会进来**。这一步同时是**安全闸门**。
- 工程库的**工作区文件可能带着历史遗留的 CRLF**（`.gitattributes` 声明 `eol=lf`，
  但加入该规则之前检出的文件不会自动改写；因为 `text` 归一，`git status` 仍显示干净）。
  直接复制工作区会把 CRLF 带进发布库，于是：
  · 与工程库做逐字节对比时出现**成百上千条假差异**（真实内容其实相同）；
  · 若随后**从工作区**生成 `SHA256SUMS.txt`，清单算的是 CRLF、而 GitHub 上的 blob 是 LF
    ⇒ 使用者更新时**逐文件校验全红**，装不上。
- `git archive` 会按 `.gitattributes` 做检出转换，产出的正是使用者下载到的字节。

> 对比两库差异时**先归一换行**再比，否则会把换行符差异当成内容差异（本书写时实测踩到，
> 一次性报出 69 条"差异"，其中 60 多条只是 CRLF）。

### 3.2 删除清单（逐条删，删完做一次计数断言）

| 类别 | 具体 |
|---|---|
| 回归脚本 | `test_*.py`、`test_*.js`、`run_all_tests.py` |
| 开发脚手架 | `codebase_testkit.py`、`migrate_scope.py`、`migrate_templates.py`、`upgrade_templates.py` |
| 团队/内部文档 | `团队协作指南.md`、`docs/LuaN1ao对比分析.md`（内部竞品分析）、**`docs/internal/`（整目录）** |
| 清单 | 删掉旧的 `SHA256SUMS.txt`，稍后重新生成 |

```bash
cd <发布库工作副本>
rm -f test_*.py test_*.js run_all_tests.py codebase_testkit.py \
      migrate_scope.py migrate_templates.py upgrade_templates.py \
      "团队协作指南.md" "docs/LuaN1ao对比分析.md" SHA256SUMS.txt
rm -rf docs/internal
# 断言：删除后文件数应明显下降（本次基线：261 → 166）
find . -type f -not -path "./.git/*" | wc -l
```

> ⚠️ 工程库还有几篇**未被跟踪**的开发文档（审计报告 / 实施规格 / 路线图等，
> 已在 `.gitignore` 里）。用 `git archive` 构建时它们**本来就不会出现** ——
> 如果你在发布库里看到它们，说明你用了文件系统复制，**回退重做**。

### 3.3 发布版专属改写（与工程库**有意不同**的文件）

| 文件 | 发布版怎么改 | 为什么 |
|---|---|---|
| `README.md` | 重写为使用者视角：快速开始 / 工作模式 / 控制台 / **更新与版本** / 与工程库的差异 / 已知限制 / 合规 | 工程库的 README 含大量开发与测试内容 |
| `CHANGELOG.md` | **新增**：按 §2.4 从《更新报告》生成，只写使用者能感知的变化 | 使用者要能一眼看出"这版改了什么" |
| `requirements.txt` | 删掉仅测试需要的 `pytest` | 发布库不含测试 |
| `VERSION.txt` | 写成三段式版本号（如 `1.001`） | 与工程库的整数版本号区分 |
| `release_repo.txt` | **新增**：第一行填发布库 `owner/repo`，其余为注释 | 更新器的拉取源 |
| `app/console_api.py` | 「跑回归」端点在测试脚本缺失时返回 `shipped: false` + 明确说明 | 发布库刻意不含 `test_068`，不能报"找不到脚本"（那看起来像安装损坏） |
| `console/views/whitebox.js` | 对应地把 `shipped: false` 显示为**中性提示** | 别把"能力有意不含"画成红色"回归失败" |
| `app/main.py` | 若有注释引用了未随库分发的文件，改成自足表述 | 免得使用者去翻不存在的文件 |

**必须逐字节一致**（可从工程库直接复制，不要手改）：`update.py` 以及除上表之外的**所有源码**。

> 待改进：上表后 3 行（`console_api.py` / `whitebox.js` / `main.py` 注释）目前仍是两库分叉。
> 目标是把它们也归一 —— 发布版那套逻辑在工程库里同样成立（测试脚本存在时那个分支永不触发），
> 归一键只需核对：工程库没有测试覆盖 `/whitebox/regress` 端点（实测确认无覆盖）。
> 完成归一后，本表只剩 `README.md` / `requirements.txt` / `VERSION.txt` 三行。

### 3.4 增量更新发布副本（**第二个版本起走这里，不要重做 §3.1~3.2**）

首次建库之后，后续每版是**增量更新**：把工程库这版改动的**运行组件**搬进已有发布副本。
**不要**再从 `git archive` 重建（会丢掉发布版的定制，还要重写历史）。

⚠️⚠️ **绝不能整文件 `cp` 覆盖** —— 发布副本里有若干处**有意与工程库不同**（见 §3.3 表，
另有 `update.py` 的内置默认源、`console_api.py` 的 `shipped:false`、`whitebox.js` 的中性提示、
`main.py` 的一句注释）。整文件覆盖会把这些**静默改回去**，而且没有任何报错。
本项目已**连踩两次**（都是 `app/main.py` 那句注释）。

正确做法（任选其一，推荐前者）：

1. **逐处合并**：在发布副本上把本版的改动**重放一遍**（用同一批编辑，而不是复制文件）。
2. 复制 + **对账**：`cp` 之后，用一份"两库同名文件差异清单"探针核对，
   确认剩下的差异**恰好**是那些"有意不同"，多出来的就是被冲掉的，立即恢复。

对账探针的思路（可写成脚本复用）：对每个两库共有的文件比较"发布副本 HEAD"与
"工程库上一个版本"，把差异逐行列出来 ——

- 差异**只在** §3.3 表 + 上面那几处 ⇒ 正常；
- 出现别的差异 ⇒ **被冲掉了**，恢复它。

> 实践数据（v1.003 / v1.004 两次）：`console_api.py` 124 行、`whitebox.js` 92 行、
> `update.py` 715 行、`README.md` 274 行属正常；`app/main.py` **恰好 1 行**（那句注释）。
> `app/registry.py` / `web/app.js` / `web/style.css` 应当**完全相同**。

同步完成后，别忘了 §5 第 2 步（`git add` 会按 `.gitattributes` 把 CRLF 归一成 LF）——
从工程库工作区复制过来的文件可能是 CRLF，**清单必须从 index 生成**才能与使用者端一致（§11.1）。

## 4. 生成 `SHA256SUMS.txt`（**只能从 git index**）

先在发布库工作副本里 `git init` + `git add -A`（见 §5 第 1~2 步），**然后**生成清单：

```python
#!/usr/bin/env python3
"""从 git index 的 blob 生成 SHA256SUMS.txt（排除自身），并逐条自检。"""
import hashlib, re, subprocess, sys
from pathlib import Path

repo = Path(sys.argv[1] if len(sys.argv) > 1 else ".").resolve()

def git(args, binary=False):
    return subprocess.run(["git", "-c", "core.quotepath=false"] + args,
                          cwd=repo, capture_output=True, text=not binary)

entries = []
for rec in git(["ls-files", "-s", "-z"], binary=True).stdout.split(b"\x00"):
    if rec.strip():
        meta, _, p = rec.partition(b"\t")
        parts = meta.split()
        if len(parts) >= 2:
            entries.append((parts[1].decode(), p.decode("utf-8", "replace").strip()))

inp = "".join(s + "\n" for s, _ in entries).encode()
data = subprocess.run(["git", "cat-file", "--batch"], cwd=repo, input=inp,
                      capture_output=True).stdout
blobs, pos = {}, 0
for _sha, rel in entries:
    nl = data.find(b"\n", pos); hdr = data[pos:nl].split()
    assert hdr[1] == b"blob", hdr
    size = int(hdr[2]); pos = nl + 1
    blobs[rel] = data[pos:pos + size]; pos += size + 1

lines = [f"{hashlib.sha256(b).hexdigest()}  {r}"
         for r, b in sorted(blobs.items()) if r != "SHA256SUMS.txt"]
(repo / "SHA256SUMS.txt").write_text("\n".join(lines) + "\n", encoding="utf-8", newline="\n")

# 自检：逐条回比 index 内容（这正是使用者端 update.exe 的比对口径）
got = {}
for ln in (repo / "SHA256SUMS.txt").read_text(encoding="utf-8").splitlines():
    p = ln.split(None, 1)
    if len(p) == 2:
        got[p[1].strip()] = p[0]
bad = [r for r, b in blobs.items()
       if r != "SHA256SUMS.txt" and got.get(r) != hashlib.sha256(b).hexdigest()]
print(f"写出 {len(lines)} 条；不一致 {len(bad)} 条 {bad[:5]}")
sys.exit(1 if bad else 0)
```

**口径要点**：内容取自 index 的 blob（不是工作区）；排除清单自身（自指算不出哈希）；
`core.quotepath=false`（中文路径按 UTF-8 直接写）；生成后**必须**逐条自检。
使用者端 `update.py` 会跳过清单里没有的条目并告警 —— 所以清单里**不包含**
`SHA256SUMS.txt` 自身是预期行为。

## 5. 建库与提交（全新历史）

```bash
cd <发布库工作副本>
git init -b main                    # 必须 main
git add -A
python <清单脚本> .                 # §4，生成 SHA256SUMS.txt
git add -- SHA256SUMS.txt
git commit -F <提交说明文件>
```

- **不引入工程库的历史**：发布库要的是"干净的一次发布"，不要带工程的历次提交。
- 若发布库远端已有 GitHub 自动生成的 `Initial commit`（一行样板 README + LICENSE）：
  · **LICENSE 要保留**（那是仓库创建时的选择，不能因为覆盖而丢掉）；
    做法：`git show <fetched-ref>:LICENSE > LICENSE` 后再 `git add`；
  · 样板 README 会被我们的 README 取代，无需保留；
  · 然后 `--amend` 把它们压进**同一个**发布提交里，别留下"补占位符"这类尾巴提交。
- 提交说明里写清：本次对应的工程库提交号、全量回归结果、以及在 §2 里列的三条使用者须知。

提交后断言：

```bash
git status --porcelain              # 期望：无输出
git ls-files | wc -l                # 记录文件数
git log --oneline                   # 期望：只有 1 个提交（正式发布）
```

## 6. 推送

### 6.1 什么时候可以用 `--force-with-lease`

只有一种情况：**远端那个提交是你已知的、无价值的自动生成提交**（如 GitHub 的 Initial commit），
且你已经把其中要保留的东西（通常是 LICENSE）并入了新提交。

```bash
git push --force-with-lease=main:<远端当前的 sha> origin main
```

- **必须显式给出 expected sha**。浅克隆或未 fetch 时 remote-tracking ref 可能不可信，
  显式比对才不会误覆盖别人在你之后推的提交。
- 若远端 SHA 与你记录的不一致 ⇒ **停下来**，说明有人推过东西，先 fetch 看清楚再决定。

### 6.2 普通追加（更常见）

远端没有需要覆盖的东西时，用普通 `push`（能快进就快进），**不要**动不动 force。

### 6.3 本机环境下的推送姿势（重要）

本机（沙箱环境）推送有两个固定故障，必须一起处理，否则会卡死或报证书错误：

- 环境注入了 `HTTP(S)_PROXY` ⇒ **push 的 POST 会被卡住**；
- 直连时 TLS 吊销检查失败（`CRYPT_E_NO_REVOCATION_CHECK`）⇒ 需 `http.sslVerify=false`；
- 而**去掉代理后凭据助手不返回 token** ⇒ 必须**先带代理**用 `git credential fill` 取出凭据，
  写进一个临时凭据文件，去掉代理后再推。

```bash
# 取出凭据（带代理）→ 只写临时文件，绝不打印内容
printf 'protocol=https\nhost=github.com\n\n' | git credential fill

# 推送（去代理 + sslVerify=false + 临时凭据文件），推完立刻删除临时文件
env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy \
  git -c "credential.helper=store --file=<临时文件>" \
      -c http.sslVerify=false -c http.proxy= -c https.proxy= \
      push origin main
git update-ref refs/remotes/origin/main HEAD     # 直推 URL 不会自动更新本地 ref
```

**绝不把 token 写进日志、命令回显或提交内容。**

## 7. 端到端验证（**必做，推完就跑**）

推上去不等于发布成功。逐条确认：

| # | 检查 | 怎么查 | 期望 |
|---|---|---|---|
| 1 | 远端分支 = 本地 HEAD | `git ls-remote origin refs/heads/main` 对比 `git rev-parse HEAD` | 完全相同 |
| 2 | 远端版本号 | `git show origin/main:VERSION.txt` | 与本地发布的版本号一致 |
| 3 | 远端清单与本地内容一致 | 抽查 3~5 个文件：`git show origin/main:<路径>` 的哈希 vs 本地 `sha256sum` | 逐条相同 |
| 4 | 更新器真正读的 URL 可达 | 访问 `https://raw.githubusercontent.com/<owner>/<repo>/main/VERSION.txt` | 返回本次版本号 |
| 5 | 敏感文件没上传 | `git ls-files` 里不应有授权白名单 / 代码库登记 / `*.db` / `artifacts/` / `config.yaml` | 全部为空 |

⚠️ **判"推上去了没"要用 git 对象，不要用 raw URL** —— `raw.githubusercontent.com` 有 CDN 缓存，
刚推完可能仍返回**旧内容**（实测：推完新版本后 raw 仍显示上一个版本号，容易误判成推送失败）。

⚠️ Git Bash 下 `git show origin/main:路径` 这类带冒号的参数需要 `MSYS_NO_PATHCONV=1`，
否则路径会被 MSYS 转换、报 `ambiguous argument`。

### 7.1 收尾：回写《更新报告》（**最容易漏的一步**）

在**工程库**里改 `docs/internal/更新报告.md`：

1. 把"待发布"里这次发布覆盖的条目**整段移入"已发布"**；
2. 在"已发布"里记下：发布版本号（三段式）、发布库提交号、以及"用户可见变更概要"
   （与发布库的 `CHANGELOG.md` 保持一致的说法）；
3. 若这次是把"待发布"清空了，写一句"下一条起重新累积"。

然后按工程库的小版本流程提交这个改动（bump `VERSION.txt` + 重建 `SHA256SUMS.txt`）。

**为什么不能漏**：报告是下一轮发布闸门的唯一依据。不回写 ⇒ 已发布的内容会继续留在
"待发布"里，下次判定时把它们当新内容、误判"攒够了"，或者反过来把真正的新内容淹掉。

## 8. 回滚

发布库是"内容型"仓库，回滚即"重新发布一个正确的版本"：

```bash
cd <发布库工作副本>
git revert --no-commit <坏的提交>   # 或直接修正文件
# 改回正确内容后：bump VERSION → 重建 SHA256SUMS（§4）→ 提交 → push
```

**不要**为了回滚去 force-push 掉已发布的提交：已经更新过的使用者手里有那个版本，
历史被改写只会让"谁装了什么"变得查不清。要让使用者回到旧版，就发布一个**更旧内容的新版本号**。

> 使用者端的 `update.exe` 自带 `update_backup_*` 备份与「回滚上次更新」按钮，
> 那是**使用者本机**的回滚，与仓库侧回滚是两件事。

## 9. 构建后守卫清单（逐条应为真）

发布提交之前，把下面这些当成 checklist（能让脚本自动断言就别靠眼睛）：

- [ ] `VERSION.txt` 是本次目标版本号，且格式与上一版**同套**；
- [ ] **§2.1 的发布闸门确实满足了**（不是"顺手发一版"）；
- [ ] `SHA256SUMS.txt` 条目数 = `git ls-files | wc -l` − 1（排除自身），且逐条自检通过；
- [ ] `release_repo.txt` 第一行 = 真实的发布库仓库名（**不是占位符**）；
- [ ] 发布库有 `CHANGELOG.md`，内容是从《更新报告》改写的使用者视角说法（无内部细节）；
- [ ] `update.py` 与工程库那份**逻辑一致**（代码行去注释后逐行相同，仅 `DEFAULT_REPO` 值不同，
      且各自指向本仓库）；
- [ ] 工程库**没有** `release_repo.txt`，且 `.gitignore` 忽略它；
- [ ] 发布库**没有** `test_*` / `run_all_tests.py` / `docs/internal/` / 开发脚手架；
- [ ] 发布库**没有**授权白名单、代码库登记、`*.db`、`artifacts/`、`config.yaml`；
- [ ] 所有 Python 文件 `py_compile` 通过；所有 JS 文件 `node --check` 通过；
- [ ] **实跑一次**发布副本（起服务 → 打关键端点 → 停），确认启动页 / 主界面 / health /
      控制台的 fail-closed（未配口令 ⇒ 403）都正常；
- [ ] 提交说明里写明了对应的工程库提交号、回归结果、以及 §2.3 的三条使用者须知；
- [ ] **发布后已回写《更新报告》**（条目移入"已发布" + 记下发布版本号与提交，见 §7.1）。

## 10. 已知坑（照抄会出事）

| # | 坑 | 后果 / 处置 |
|---|---|---|
| 1 | 用文件系统复制代替 `git archive` | 换行符混入 + gitignored 本机数据可能混入；发布库内容与使用者下载的字节不一致 |
| 2 | 清单从工作区生成 | 使用者端逐文件校验**全红**，装不上（见 §11.1） |
| 3 | 忘了 bump `VERSION.txt` | 使用者的更新器判定"已是最新"，新内容**推不下去** |
| 4 | `VERSION.txt` 与 `SHA256SUMS.txt` 不在同一 commit | 同上：中间那个提交的版本是自相矛盾的 |
| 5 | 提交了内部流程文档 / 测试脚本 | 使用者平白拿到一堆开发垃圾；内部文档本不该公开 |
| 6 | 提交了 `release_repo.txt` 到工程库 | **所有人**的更新器静默改拉另一个库，现象只是"更新后版本没变" |
| 7 | 用 raw URL 判断推送结果 | CDN 缓存导致误判（见 §7） |
| 8 | 无脑 `--force` | 覆盖别人的提交；只能用 `--force-with-lease=<ref>:<sha>` 且 sha 对得上才推 |
| 9 | 用后台 `nohup ... &` 跑长任务（如全量回归） | 进程会被回收，日志为空 ⇒ 以为跑过了其实没跑。用受管后台任务 |
| 10 | 改文件后不复核 | "编辑成功 ≠ 内容还在"；改完立刻回读关键串 |
| 11 | 守卫/扫描器自己误报 | 负向检查只匹配**调用形态**，不要匹配裸字符串（注释里的解释性引用会被误判） |
| 12 | 发布完**不回写《更新报告》** | 已发布内容继续留在"待发布" ⇒ 下次闸门误判"攒够了"，或把真正的新内容淹掉（见 §7.1） |
| 13 | 一有改动就发正式版 | 版本号刷太密 ⇒ 使用者不再认真看更新内容，也白白消耗构建与验证成本（见 §2.1） |
| 14 | 拿"逐字节一致"核对两库 `update.py` | 自发布库 1.002 起内置默认源**按设计不同** ⇒ 这条会误报。改比"逻辑行"（见 §0 硬约束 1） |
| 15 | 用 raw URL 判断"发上去了没" | 除 CDN 缓存外，**本机 hosts 可能把 `raw.githubusercontent.com` 钉到 `127.0.0.1`**（加速器的屏蔽段），本机访问会直接挂住超时 —— 那是本机环境问题，**不是发布失败**。核对一律用 git 对象（见 §7） |
| 16 | 修了使用者能感知的问题却**不 bump `VERSION.txt`** | 已装旧版的使用者点更新会判定"已是最新"，**修复到不了他手上**。发布会话里出现过一次（1.001 内容覆盖），只能再发一版补救 |

## 11. 补充说明

### 11.1 为什么清单必须来自 git index

发布库的发布流程是"index → 清单 → commit"，使用者端更新器拉的是 GitHub 上的
**blob 内容**（zipball）。只有从 index 生成，清单才与使用者拿到的字节**同源**。
从工作区生成时，`core.autocrlf` / `.gitattributes` / 历史遗留 CRLF 任意一项都能让两者错位，
而错位在**使用者那一侧**才爆炸（校验失败、装不上），你这边看不出任何异常。

### 11.2 两库"有意不同"与"必须相同"

- **必须相同**：所有源码（`app/`、`console/`、`web/`、`data/kb`、`data/rules` …）、`update.py`。
- **有意不同**：`README.md`、`requirements.txt`、`VERSION.txt`，以及 §3.3 表中尚未归一的三处。
- 判断方法：对比前**先归一换行符**，否则你会收到一堆假差异。

### 11.3 发布库的"最小验证"（没有测试脚本怎么办）

发布库刻意不含测试，所以只能**实跑**：起服务 → 逐端点打一圈 → 停服务。
至少要覆盖：起始页、作战界面、`/api/health`、`/api/tools`、`/api/projects`、
控制台登录页、以及**未配口令时控制台接口返回 403**（fail-closed）。
